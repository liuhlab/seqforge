    seqforge¶

    seqforge reads public sequencing studies and their files, and writes down what they are, so that each dataset can be processed the right way. It does two jobs.

    • It reads a study. Given a GEO Series, it works out which records and papers make up the study (the study's bounds). Then it works out what each sample was: the factors the study varied on purpose, each sample's level of each, and labels such as species, tissue and assay (the study's reading).
    • It compiles a dataset. Given FASTQ files, it works out from the bytes which sequencing technology made them and which file holds what. Then it writes a pipeline that you submit to a cluster.

    One report shows a study's bounds and reading, a compiled dataset, or both, on one web page. See three example reports before you read on.

    What goes in, and what comes out¶

    You give it It writes What the file is for
    A GEO Series id bounds.yaml The Series and papers that make up one study, and the records left out
    The bounds reading.yaml What each sample was. Each claim carries a quote, or says it is inferred
    FASTQ files, and if you have them an accession and a paper manifest.yaml What the data is: technology, read roles, samples. One per dataset, and it never changes
    A genome and an annotation processing.yaml The recipe: what to do with the data. A dataset can have many
    The manifest and a recipe A Snakefile and its config The pipeline you submit. It ends in one count matrix (.h5ad) per sample
    Any of the above report.html One page to read it all

    The two halves run on their own. A study can be read without compiling any of its files, and a dataset can be compiled with no study at all. They meet in the sample table: when you compile with --study, each sample's row takes the reading's factors and labels, matched by its BioSample accession (the archive's id for the biological sample). The manifest does not change.

    Why you can trust it¶

    • A model answers only where code can check the answer. In a reading, every claim quotes a passage that code finds again, word for word, in the record or paper. A claim with no such passage is marked inferred.
    • Each question is asked twice. The second time, the options come in reverse order. If the two answers differ, the study is marked unsettled, so you know which answers to check.
    • The bytes decide the technology. A paper that names a kit is a hint. The reads in the files decide, and when the two disagree, seqforge stops and says so.
    • It refuses rather than guesses. A refusal is an exit code with a reason and a suggested fix, not a best guess.
    • It never reads a whole FASTQ file. A small, fixed head of each file is enough.
    • Every study file and manifest is checked against its written format before it is saved.

    Why you can trust the output explains each point.

    Where it stands¶

    The study chain is built and run on the standard set, 50 GEO studies picked to cover many designs. Most of them settle, and a first run costs a few cents a study in model calls. The dated note on the latest run gives the counts and the cost. Nothing on this site scores those readings against a person's answers: measuring accuracy is a separate effort.

    What it does not do¶

    • It does not submit jobs. You run the Snakefile on your own cluster.
    • It does not judge its own accuracy.
    • Reading a study needs the lab's model gateway and its copy of the GEO and SRA records. Compiling calls the gateway only to read prose, such as a paper or the archive's records, and seqforge run --no-llm skips that step.
